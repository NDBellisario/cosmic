The Autonomous Decision Loop

A three-tier architecture: a planner that writes goals, an SLM that judges & chooses, and a game engine that acts — joined by one narrow contract.

The three tiers

Each tier owns one job and hands a narrow artifact to the next. The boundaries are the whole design: a small, unreliable model is only ever asked to do what it is good at, and everything it can get wrong is observable, reversible, or vetoed downstream.

Tier 1 — Orchestration Claude Opus · offline

The strategist. Authors what the bot should want.
Writes SOUL.md (personality) & GOAL.md (the goal list + content)
Grounded by world-index (grind / quest / gear, from real WZ + DB data)
Owns goal content exclusively — the only writer of goal text
Reviews the SLM's completion disagreements; re-authors on escalation
▼GOAL.md — goal content (Tier 1 writes, Tier 2 only flips status)

Tier 2 — Decision SLM · qwen2.5:7b · in-JVM

The judgment layer. Reads the world, decides what to do next — never reimplements how.
Reads GOAL.md + live game state every tick (sweep 8s / heartbeat 60s)
Judges which goals are complete (with literal evidence)
Flips only the per-goal status flag — never the goal text
Emits one action from a fixed vocabulary; the harness owns control flow

Prototype today: in-process Java (BotAutonomousPlanner) calling Ollama. Destined to become an external per-bot agent (Rust) for production perf — same contract, different host.

▼BotTask — one action from a fixed vocabulary

Tier 3 — Execution Cosmic engine · Java · deterministic

The body. A battle-tested 61-file framework that turns a chosen action into pixels.
Executes BotTasks: A* navigation, combat, movement, inventory
Auto-handles AP/SP + job advancement, gear optimize/buy, potions
Deterministic — no SLM ever runs on the game-tick thread
Reports state back up via the situation snapshot each tick

Why it survives a small, unreliable model

  • Deterministic / probabilistic split. Facts, thresholds, sequencing, and writes live in code. The SLM only makes soft judgments — “is this done?”, “what next?” — never arithmetic or control flow.
  • Content vs. status ownership. Tier 1 owns goal text; the harness only toggles a per-goal status flag. The model can never corrupt the goals themselves.
  • Two-tick confirmation. A goal must be judged complete on two consecutive ticks before its flag flips — a single false-positive judgment is vetoed by the next tick.
  • Literal evidence. Every verdict cites a copied key=value from state (level=35), never prose — so the SLM-vs-Opus disagreement set is auditable.
  • Stuck-detector. If a stubborn false-negative stalls the batch, after K ticks the harness signals Tier 1 anyway — one bad judgment can’t freeze the bot forever.
  • Atomic writes. GOAL.md is read every tick (and by the chat responder) while it’s flipped; the write is temp-file + rename(2), so a reader never sees a torn file.
  • Constrained JSON. Both SLM calls force format:"json" — far more reliable than free-form function-calling at 1–3B.

The grounding substrate

world-index SQLite, from WZ + MySQL

grind (where to hunt) · questroute (what to do) · gear / sources (what to wear & where to get it). Tier 1 queries it so every authored goal cites a real id.

SOUL.md / GOAL.md per bot, hot-reloaded

SOUL = who the bot is (drives chat and decisions). GOAL = the ordered goal list with harness-owned status flags. Both reload live every tick.

The loop & its safeguards, observed in production logs

✓
Flip exactly once, after two consecutive done-judgments. A genuinely-complete goal (level=35 ≥ 30) flipped on the 2nd consecutive verdict — and only then.
✓
Two-tick vetoed a false positive. The 7b judged “earn 10m mesos” done at 5m on one tick; the next tick disagreed, the counter reset, and it did not flip.
✓
Stuck-detector caught a false negative. The 7b stubbornly refused to mark “reach level 33” done at level 35; after 5 ticks the harness signalled Tier 1 anyway — the batch never froze.
✓
Atomic write holds under concurrent reads. A reader looping over GOAL.md during 300 flips never saw a torn file (the test drove a rename(2) hardening).
